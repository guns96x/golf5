### C1. Пошкодження заголовка карти дає verdict PASS

**Файл:** `calharness/diff_engine.py:449` + `calharness/safety_validator.py:190`

`_analyze_map_diff()` повертає `header_changed=False` жорстко, константою.
`SafetyValidator` читає саме це поле (`any(m.header_changed for m in ...)`),
а не `bytes_by_category[MAP_HEADER]`, який диф якраз коректно рахує.

**Відтворено** (nx карти `PCR_pBDesBas_MAP` змінено 16 → 18):

```

categories: {'MAP_HEADER': 1}
maps_changed: []
is_clean_calibration: True
VERDICT: PASS | hard_fails: 0
  -> RULE_MAP_HEADERS_INTACT PASS | "All map dimension headers are intact."
```

Валідатор прямо стверджує, що заголовки цілі, маючи в тому ж звіті байт,

карти кинув виняток, який проковтнув `except Exception: pass`

правило має дивитись і на `bytes_by_category`, і на `header_changed`.

**Regression test:** той самий сценарій + `assert audit.overall_verdict == HARD_FAIL`
і `assert "RULE_MAP_HEADERS_INTACT" in fail_rules`.

### C3. 512 KB читання калібрувальної зони класифікується як модифікація коду

**Файл:** `calharness/diff_engine.py:333` (`if addr < 0x180000: return CODE_AREA`)
та `_build_intervals()` / `compare()`

`MapDecoder` коректно тримає `base_address = 0x180000` для 512 KB образу.
`SemanticDiffEngine` цього не робить взагалі: він порівнює **зсуви у файлі**
з **абсолютними адресами ECU** з A2L і з жорсткими діапазонами.

**Відтворено** (один байт усередині `PCR_pBDesBas_MAP` у 512 KB зрізі):

```
decoder OK on 512KB: PCR_pBDesBas_MAP (16, 10) max 2050.0 hPa
bytes changed: 1
categories: {'CODE_AREA': 1}
VERDICT: HARD_FAIL
  HARD_FAIL: RULE_CODE_AREA_INTACT | "Code area modified: 1 bytes changed in
             executable firmware space (< 0x180000)."
```

Тобто заявлена підтримка «2MB full flash + 512KB calibration read» справджується
для декодера й для checksum-інспектора, але **не** для диф-енджина й валідатора.
А саме вони дають вердикт.

**Як виправити:** ввести один тип `AddressSpace` з явним перетворенням
`file_offset <-> ecu_address` і прогнати через нього і диф, і діапазони,
і `_build_intervals`. Зараз `decoder.base_address` і `checksum.base_offset`
означають **протилежні речі** з майже однаковою назвою — це пастка.

**Regression test:** той самий діф на 2 MB і на 512 KB зрізі того самого файлу
мусить давати ідентичні категорії й вердикт.

### C4. Розміри A2L-об'єктів угадуються → масові фальшиві UNMAPPED

**Файл:** `calharness/diff_engine.py:194-235` (`sz = 2` за замовчуванням)

A2L цього проєкту використовує **41 record layout** у характеристиках.
Диф знає 2 з них плюс чотири 1/4-байтові спецвипадки; решта отримує `sz = 2`.

Перевірено по A2L: `Carb_Mode1Signal_CA` — `VAL_BLK`, `Kwb_Wu16`, `NUMBER 40`,
тобто **80 байтів** (і `DP_BLOB` у тому ж блоці прямо каже `0x50`).

**Відтворено** (змінено весь 80-байтовий VAL_BLK):

```
{'KNOWN_CALIBRATION': 2, 'UNKNOWN_CALIBRATION': 78}
VERDICT: HARD_FAIL
```

78 із 80 байтів повністю описаного в A2L об'єкта оголошені «без власника».
`VAL_BLK` у цьому A2L — **2 145 штук**. Для 1-байтових layout-ів (`Kw_Wu8`,
3 003 штуки) помилка протилежна: інтервал на байт довший за об'єкт і **claims
чужий байт**, тобто дає неправильного власника без жодної ознаки помилки.

**Як виправити:** будувати розміри з розпарсеного `RECORD_LAYOUT`
(`FNC_VALUES` dtype + `NO_AXIS_PTS_*`/`AXIS_PTS_*`) плюс `NUMBER` для `VAL_BLK`
плюс довжина з `IF_DATA DP_BLOB` як перехресна перевірка. Якщо розмір не
виводиться — об'єкт має потрапляти в явний список `UNSIZED`, а не отримувати 2.

**Regression test:** для кожного з 41 layout — один об'єкт, і `assert`, що
обчислений розмір інтервалу дорівнює довжині з `DP_BLOB`.

### C5. Ідентифікація ECU повертає НЕ той парт-номер

**Файл:** `calharness/decoder.py:65-69`

`get_identity()` бере **перший** рядок, що підходить під
`^03G906021[A-Z0-9]{1,2}$`.

**Відтворено** на власному стоковому файлі проєкту:

```
vag_part_number: '03G906021AB'      <- НЕПРАВИЛЬНО
bosch_sw_number: '1037391847'       ok
vag_sw_version:  None
```

У бінарі рівно два такі рядки: `03G906021AB` за `0x1C0CBE` і справжній
`03G906021QJ` за `0x1C0CD2`. Регекс ловить перший.

Тобто функція «Open BIN → identify ECU», яка в плані GUI стоїть другим пунктом,
на еталонному файлі цього ж проєкту відповідає неправильно — і мовчки.

Додатково: `vag_sw_version` **завжди** `None`. Рядки збираються регексом
`[A-Za-z0-9_]{5,}`, тож усі елементи мають довжину ≥ 5, а перевірка —
`"1984" in ascii_strings` (точне членство 4-символьного рядка). Умова
нездійсненна за побудовою. Байти `1984` у файлі є (рівно один раз).

**Як виправити:** ідентичність читати за **адресами з A2L**
(`EepInit_stVAGPrtNo_C` та сусідні), а не пошуком по всьому образу; при кількох
кандидатах — повертати всі й вимагати однозначності, а не `break` на першому.

**Regression test:** `get_identity()` на стоковому файлі мусить дати
`03G906021QJ` / `1984` / `1037391847` / `391847`, і мусить **падати або
повертати ambiguity**, якщо кандидатів більше одного.

### C6. WOT_CONFIRMED може підтверджуватись каналом, який не є педаллю

**Файл:** `calharness/log_analyzer.py:340` та `:672-676`

```python
pedal = float(row.get("Throttle_pct") or row.get("Pedal_pct") or 0.0)
```

`Throttle_pct` має **пріоритет** над `Pedal_pct`. На TDI «throttle» у VCDS —
це дросельна заслінка (EGR-клапан упуску), а не педаль: вона відкрита ~100 %
на більшості режимів і **прикривається** під EGR. Далі `classify_pull_kind()`
оголошує `WOT_CONFIRMED`, якщо «педаль» ≥ 95 % на ≥ 70 % проїзду.

Отже найсильніша мітка в системі може ставитись із каналу, який фізично не є
свідченням повного натискання. Це рівно та підміна, яку забороняє
`golf5/CLAUDE.md` («назва каналу ≠ доведена величина»).

**Як виправити:** `WOT_CONFIRMED` має вимагати **названий канал педалі** з
явного whitelist (`Accelerator_Pedal_pct`, `AccPed_rAPP`), а `Throttle_pct`
взагалі не має права впливати на цю мітку. Немає каналу — `WOT_UNKNOWN`,
а не пониження до `WOT_LIKELY`.

**Regression test:** лог із лише `Throttle_pct=100` → результат **не**
`WOT_CONFIRMED`.

### C7. Нулі в каналах лімітерів дають «SMOKE_LIMITER 100 %»

**Файл:** `calharness/log_analyzer.py:825-847` (і дзеркально `:866-888`)

```python
m = min(d, t, s)
if abs(s - m) < 0.5: smoke_cnt += 1
```

Якщо `trq_request = trq_limit = trq_smoke = 0` (а в цьому проєкті вже
встановлено, що канали лімітерів пишуться нулями), то `m = 0`, перша умова
істинна на кожній точці → `SMOKE_LIMITER 100 %`, і це потрапляє у
`diagnostic_findings` реченням «Fuel delivery is bottlenecked by the Smoke
Limiter». Діагноз із порожніх даних.

У гілці VCDS WOT це випадково не спрацьовує лише тому, що там інший дефект
(див. C8) занулює канали в `None`.

Додатково: збіги розв'язуються **порядком if**, не позначаються як збіг, тож
smoke систематично переоцінений; допуск `0.5` застосовується і до Нм, і
`0.2` до мг без жодного обґрунтування.

**Як виправити:** вимагати, щоб канал мав ненульову дисперсію в межах проїзду,
інакше `LimiterBottleneck.UNKNOWN` + явний запис `channel_flatlined`.
Збіг у межах допуску — окрема категорія `TIED`, не `SMOKE`.

**Regression test:** сегмент із трьома нулями → `UNKNOWN`, а не `SMOKE_LIMITER`.

### M1. Кеш A2L не прив'язаний до вмісту A2L

**Файл:** `calharness/a2l_catalog.py:69-73`

```python
self.db_path = self.cache_dir / (self.a2l_path.stem + ".a2ldb")
if self.db_path.exists(): self.session = pya2l.open_existing(...)
```

Ключ кешу — лише ім'я файлу. Якщо A2L виправлять або підмінять, зберігши ім'я,
система вічно декодуватиме зі старої бази й ніколи про це не скаже. Для проєкту,

звіряти при відкритті. `DecodedMap`, `SemanticDiffReport`, `SafetyAuditReport`

### M3. Layout інтерпретується за НАЗВОЮ, а не за визначенням

**Файл:** `calharness/decoder.py:125-146`

Декодер зіставляє рядок `"Kf_Xs16_Ys16_Ws16"` і зашиває структуру (`>hh`,
`>i2`, `reshape((nx, ny))`). Реальний `RECORD_LAYOUT` у A2L каже:

```
Kf_Xs16_Ys16_Ws16:  NO_AXIS_PTS_X 1 SWORD / NO_AXIS_PTS_Y 2 SWORD /
                    AXIS_PTS_X 3 SWORD / AXIS_PTS_Y 4 SWORD /
                    FNC_VALUES 5 SWORD COLUMN_DIR DIRECT
```

Тобто `reshape((nx, ny))` **правильний** — але тільки тому, що порядок
`COLUMN_DIR`, а не тому, що код це перевірив. У всьому A2L 36 з 36 `FNC_VALUES`
мають `COLUMN_DIR`, отже припущення зараз тримається; воно ніде не стверджене
і мовчки зламається на іншому A2L.

Так само зі знаковістю: зашито `>i2` (signed). У цьому A2L серед `FNC_VALUES`
є `UWORD` (7 layout-ів), `UBYTE` (10), `ULONG`, `SLONG`, `SBYTE` і
**`FLOAT32_IEEE` (3)**. Щойно хтось додасть підтримку `Kw_Wu16`, скопіювавши
наявний `elif`, з'явиться клас помилок «raw ≥ 0x8000 → від'ємне фізичне».

**Виправлення:** розпарсити `RECORD_LAYOUT` один раз і декодувати з нього
(порядок, dtype, позиції), як це робить перевірений `golf5/tools/calmath/a2l.py`.
Тоді 41 layout закриється однією реалізацією замість чотирьох `elif`.

### M5. Правило мовчки не виконується, якщо карти немає в дифі

**Файл:** `calharness/safety_validator.py:242` (`if param and param in maps_by_name:`)

Немає `else`. Якщо цільова карта не змінилась, або не задекодувалась
(див. C1/C4), правило **не дає жодного результату** — ні PASS, ні FAIL, ні
запису. Воно просто зникає зі звіту, а `overall_verdict` може стати `PASS`.

Глибша проблема: валідатор оцінює **тільки дельти** відносно еталона. Файл,
у якому наддув абсолютно небезпечний, але такий самий, як в еталоні, дає PASS.
«Безпека» тут визначена відносно довільного reference-BIN, а не відносно
файлу, який збираються заливати. Тим часом сам еталон —
`reference-from-hex.analysis-only.bin` — за документацією проєкту
**реконструйований з hex і ніколи не знятий з ECU**.

**Виправлення:** додати рівень `NOT_EVALUATED` і завжди його записувати;
оцінювати абсолютні значення карти-кандидата, а не лише дельту.

### M6. Сесії VCDS з різних днів зшиваються в одну шкалу часу

**Файл:** `calharness/log_analyzer.py:480` (`time_offset += t_rel[-1] + 10.0`)

Окремі сесії склеюються синтетичним проміжком 10 с. Проміжок більший за
`max_interpolation_gap_s = 2.5`, тож інтерполяція через шов не проходить — це
добре. Але:

* `segment_wot_pulls()` **не перевіряє розриви в часі взагалі** — він працює
  зі списком точок і порівнює сусідів за індексом. Сегмент може перетнути шов;
* метадані парсяться регексом `,(\d{1,2}),[^,]*,(\d{4}),(\d\d:\d\d:\d\d)` —
  день, рік, час, **без місяця**, і ніде не звіряються між сесіями;
* `total_duration_s` для такого файлу — фікція.

**Виправлення:** сесія має бути окремою сутністю з власною шкалою; сегменти не
можуть перетинати межу сесії; розрив у часі > N × медіанний крок розриває сегмент.

### M7. Мапінг груп VCDS за рядком-міткою, з позиційними каналами

### M9. Провенанс правил — самозаявлений текст і крихкі claim_id

**Файл:** `calharness/rules.py:91-97`

```python

citation="Offsets 0x010150, 0x040010, 0x180010, 0x1C0010, 0x1C0CBE verified to
          hold part number and SW ID strings."
```

Слово «verified» тут — речення в літералі Python. Жоден тест не читає ці зсуви
й не перевіряє, що там справді рядки ідентичності. Це та сама конструкція,

**Виправлення:** `PROJECT_VERIFIED` має підтверджуватись тестом, що читає

### M10. Надто широкі діапазони checksum ковтають калібрувальні байти

**Файл:** `calharness/diff_engine.py:56-59`

Діапазони по 16 байтів (`0x1BFFF0..0x1C0000`), тоді як саме контрольне слово —

### M11. `is_clean_calibration` ігнорує осі, заголовки й padding

**Файл:** `calharness/diff_engine.py:137-144`

Перевіряє лише `code == 0 and identity == 0 and unmapped == 0`. Змінені вузли
осей, змінені заголовки і будь-що в зоні `PADDING` (`0x1FE000..0x200000`)
не впливають на «чистоту». Пейлоад у padding проходить як clean.

### M12. MAF-конверсія правильна, але походження каналу втрачається

**Файл:** `calharness/log_analyzer.py:507`, `:596`

```python
maf_mg = (maf_gs * 1000.0) / (rpm / 60.0 * 2.0)
```

Математика **вірна** для 4-циліндрового 4-тактного: тактів впуску за секунду =
`(rpm/60) × (4/2)`, отже мг/такт = `г/с × 1000 / ((rpm/60) × 2)`. Перевірив
окремо — помилки тут немає.

Дві проблеми все ж є: `2.0` — це зашитий наслідок «4 циліндри», без імені й
коментаря; і результат кладеться в те саме поле `maf_act_mg`, що й **виміряне
ECU** значення мг/такт із групи 003. Похідний proxy і зчитаний канал стають
нерозрізнюваними — рівно та підміна, від якої застерігає `golf5/CLAUDE.md`.

### M13. Висновки в `diagnostic_findings` стверджують механізм

**Файл:** `calharness/log_analyzer.py:964-978`

> «ECU governor commanded maximum vane opening to vent excess boost»
> «Fuel delivery is bottlenecked by the Smoke Limiter»

Перше — інтерпретація напрямку шпаруватості N75 (у цьому проєкті напрямок
**виміряний**, але тут він просто заявлений у тексті без посилання).
Друге — наслідок евристики з допуском 0.5, поданий як факт.

**Виправлення:** finding має нести `evidence` і `confidence`, як це вже зроблено
для правил. Формулювання — спостереження («N75 досяг 9.8 % на 0.4 с»), а не
механізм.

3. **Відмова від автофіксера checksum — правильне рішення** і воно витримане
   в коді, а не лише в README.

4. **Розділення `UNVERIFIED` / `NEEDS_EVIDENCE` — сильна ідея.** Те, що

## 6. CORRELATOR DESIGN

Сам напрям правильний. Але **головного компонента перед ним бракує**, і він
не той, про який зазвичай думають.

### Те, чого бракує: контракт «канал логу → вхідна змінна осі A2L»

Перевірив осі у самому A2L:

| Карта | Вісь X | Вісь Y | Одиниця Y |
|---|---|---|---|
| `PCR_pBDesBas_MAP` | `Eng_nAvrg` | **`PCR_qDes`** | mg/hub |
| `PCR_rBPCtlBas_MAP` | `Eng_nAvrg` | **`PCR_qCtl`** | mg/hub |
| `FMTC_trq2qBas_MAP` | `Eng_nAvrg` | `CoEng_trqInrSet` | Nm |
| `FlMng_qPresSmoke_MAP` | `Eng_nAvrg` | **`FlMng_pIATCorr_mp`** | **hPa** |
| `AccPed_trqEng0_MAP` | `Eng_nAvrg` | `AccPed_rAPP` | % |

Три наслідки:

1. **Приклад із плану — «RPM 1850 + IQ 52 mg → `PCR_pBDesBas_MAP`» — підставляє
   не ту змінну.** Вісь Y цієї карти — `PCR_qDes`, внутрішня уставка контура
   наддуву. Це **не** `Driver_Wish_IQ`, **не** впорскування з групи 013 і
   **не** MAF-похідне паливо. У цьому ж проєкті вже встановлено, що канали
   `Driver_Wish_IQ` / `Torque_Limit_IQ` / `Smoke_Limit_IQ` пишуться нулями.
   Отже підставити «IQ» у цю вісь — означає отримати впевнені координати
   комірок із величини, яка не є віссю.

2. **`FlMng_qPresSmoke_MAP` узагалі не «rpm × паливо»** — друга вісь це тиск
   (hPa). Будь-яка спроба корелювати її «по IQ» дасть координати з нічого.

3. **Пастка одиниць, яку код не побачить.** `TorqueToFuelConverter` повертає
   значення з `FMTC_trq2qBas_MAP`, чий COMPU_METHOD — `InjMassCyc` (**mg/cyc**),
   і цим збирається годувати вісь `PCR_qDes`, чий COMPU_METHOD — `InjMass`
   (**mg/hub**). Перевірив коефіцієнти: обидва `[0, 100, 0, 0, 0, 1]` —
   **числа масштабуються однаково, а одиниці різні**. Тобто помилка не виявить
   себе ні винятком, ні дивним значенням. Це найгірший вид помилки одиниць.

### Що будувати замість «одразу корелятора»

**Крок A — `SignalContract` (обов'язково перший).**
Явна, версіонована таблиця: `log_channel → a2l_input_quantity → unit →
source_kind → status`. Заповнюється вручну, кожен рядок має статус
`VERIFIED` / `PROXY` / `UNAVAILABLE`. Корелятор **відмовляється** працювати з
осі, для якої немає рядка зі статусом `VERIFIED`, і повертає
`drop_reason: NO_VERIFIED_SIGNAL_FOR_AXIS` — що вже правильно передбачено
в чернетці через `drop_reasons`.

Для `PCR_qDes` чесний статус сьогодні — `UNAVAILABLE`. Це нормальний результат:
корелятор покаже, що по осі X (`Eng_nAvrg`) дані є, а по Y — ні, і назве, який
саме канал треба зняти. Це вже корисно й це не вигадка.

**Крок B — перевірка одиниць у рантаймі.**
`AxisSignal.unit` звіряти з `DecodedMap.x_axis.unit` / `y_axis.unit` **строго**,
з таблицею дозволених еквівалентів. `mg/cyc` ≠ `mg/hub`, доки хтось явно не
задокументує перетворення. Зараз обидва поля є, але ніде не звіряються.

**Крок C — exposure без інтерпретації.**
Те, що вже в чернетці: білінійні ваги, `sum == 1.0`, `is_clamped`,
`cell_hit_matrix`. Додати тільки: кожна `PointCorrelation` має нести
`a2l_sha256` + `bin_sha256` + id контракту сигналу.

**Крок D — і тільки потім «де стався overshoot».**
Формулювання має лишитись просторовим: «у момент максимального перельоту
двигун працював у зоні X=[i,i+1], Y=[j,j+1] карти `PCR_pBDesBas_MAP`»
— без слова «через». Причинність з exposure не випливає: та сама комірка
активна і в проїздах без перельоту.

**Чого не робити:** не виводити `PCR_qDes` з моменту через `FMTC_trq2qBas_MAP`
і не називати результат `MEASURED`. Ланцюг «Nm → mg через карту → координата
в іншій карті» складає похибки двох калібрувань і однієї інтерполяції; статус
такого числа — `DERIVED` з явною похибкою, і для вердикту воно не годиться.

## Що НЕ перевірено в цьому ревю

* `tools/calmath_engine.py` (973 рядки) і `ecu-kb/` — поза межами `calharness`.
* `tests/test_calmath.py`, `test_log_analyzer.py`, `test_map_decoder.py`,
  `test_checksum.py` — прочитані вибірково; сюїт не запускався через C0.
* Чи справді `0x010150`, `0x040010`, `0x180010`, `0x1C0010` містять рядки
  ідентичності — не перевірялось (перевірено лише `0x1C0CBE`, і там знайдено
  **два** парт-номери замість одного).
* `Gkf_Ws16` — встановлено форму (16 × 14 SWORD = 448 байтів, `COM_AXIS`)
  за A2L та кроком адрес, але не декодовано фактично.
